# PRD：New API Prompt 采集与用量统计（精简版）

状态：需求草案；第一阶段范围已确定，部署参数待核验。依据为现有《New API 管理员统计精简方案》；这里描述拟建能力，不代表已上线。

## Problem Statement

管理员需要了解谁使用了 New API、使用了哪个模型、消耗多少 Token，并能检索获准采集的用户 Prompt。现有普通文本消费日志有用户、凭证与用量，却没有可用于通用查询的 Prompt 正文；直接依靠日志无法完成输入采集。不同客户端和流式调用又使逐请求关联、隐私保护与统计口径容易出错。

## Solution

第一阶段部署一个轻量采集服务，透传客户端原有 Key 和请求到 New API，仅在已启用的接口范围内提取有界的用户文本副本，脱敏后异步保存；从 New API 原生消费日志独立同步全量用量，以网关请求 ID 关联采集记录、用户与 Token，并提供仅管理员可用的查询。推理转发不能等待分析写库，流式响应逐块回传，回答正文不采集。

第二阶段才增加离线场景分类、标签质量复核和场景统计；第一阶段不调用分类模型，也不展示场景比例。

## User Stories

1. 作为客户端用户，我希望继续使用原有 Key 和接口，以便不改变既有调用方式。
2. 作为客户端用户，我希望流式首包、后续数据和取消行为保持原样，以便采集不干扰推理。
3. 作为管理员，我希望按日期、用户和模型查看调用与输入／输出 Token，以便了解整体用量。
4. 作为管理员，我希望看到未采集 Prompt 的原生用量也计入总量，以便避免低估。
5. 作为管理员，我希望按用户、日期、模型和请求 ID 检索已脱敏 Prompt，以便排查实际使用内容。
6. 作为管理员，我希望区分每次代理请求与对应的原生消费事件，以便查看同一次请求的正文和用量而不重复计数。
7. 作为管理员，我希望看到账号和凭证标识及其可信归属，以便区分不同使用者，且不把共享 Key 的调用误认成真人。
8. 作为管理员，我希望看到采集失败、无网关请求 ID、日志延迟或未匹配的状态，以便知道报表覆盖范围。
9. 作为管理员，我希望区分上游报告、网关估算和缺失的 Token，以便不把缺失值解释为零。
10. 作为安全负责人，我希望正文只在明确启用的范围内采集并在第一份持久副本之前脱敏，以便控制敏感信息暴露。
11. 作为安全负责人，我希望只有服务端核验的管理员可读取正文和统计，以便普通用户不能越权查询。
12. 作为安全负责人，我希望正文有大小限制、保留期和关闭开关，以便采集符合已批准的用途和期限。
13. 作为运维人员，我希望队列满、写库失败或脱敏失败时推理仍可用，且有丢弃计数，以便识别数据缺口。
14. 作为运维人员，我希望日志同步可以回补并去重，以便重启和重复拉取不导致重复用量。
15. 作为管理员，我希望第二阶段再按固定类别查看离线分类结果和覆盖率，以便不把未分类请求当作已识别场景。

## Implementation Decisions

- 范围以当前精简方案为准：一个服务承载前置转发、采集、后台日志同步与管理查询，分析数据放在现有 MySQL/PostgreSQL 的独立表；不修改 New API 原生 `logs` 表。实际数据库、版本和部署拓扑先核验。
- 入口保留原 Key 由 New API 鉴权；代理不以客户端自填 `user`、用户头或 IP 确定身份，也不保存明文 Key。若发现共享 Key，只标为凭证／团队归属，不宣称可定位真实个人。人名映射仅使用经核验的账号或 `token_id` 映射。
- 第一阶段分开两个逻辑数据集：采集请求保存本地请求 ID、部署 ID、网关请求 ID、时间、接口、传输及采集状态、脱敏用户文本；用量镜像保存稳定源事件标识、日志类型、网关请求 ID、用户及凭证 ID、模型、输入／输出 Token、quota 与用量来源。不要提前写入分类标签或分类任务。
- 网关响应头 `X-Oneapi-Request-Id` 与原生日志 `request_id` 在同一部署内关联；代理本地 ID 标识入口请求。源事件去重后再按网关请求 ID 聚合，允许一次请求关联多条不同类型的日志，不以请求 ID 单独去重全部事件；缺失关联保留状态。
- 同步原生日志的完整消费范围，而不是仅同步有正文的请求。固定查询时间窗、重叠回补、幂等写入；源事件键与游标必须按实际日志后端验证，不能采用 API 展示序号作为通用游标。消费日志用于运营统计而非原子财务账本。
- Token 以消费事件为依据，区分 `reported`、`estimated`、`missing`；缺失为 null，不填零。输入／输出总量与缓存、推理等子项不能重复加总。调用数按入口请求口径，消费事件数另列，不以所有日志行数充当调用数。quota 明确标为网关额度而不是供应商成本。
- 对明确开启的部署与接口实施有界文本采集；仅提取获准的 user 文本，记录所支持的协议和提取版本，不把重传上下文直接称为“本轮新增输入”。不支持协议、媒体、过大请求、非成功响应或脱敏失败仅记必要元数据和跳过原因。采集开关关闭时不得产生正文副本。保留原请求字节转发，不保存回答正文。
- 采集副本先执行字段白名单和凭证／常见敏感信息清理，再进入有界内存队列与数据库；队列或分析库故障只影响采集并可计数，不阻塞推理。此方案不承诺进程崩溃时正文零丢失。明确并配置正文保留期，覆盖队列、日志和备份策略。
- 流式响应保持 SSE 逐块转发和取消传播；不以 HTTP 200 或连接 EOF 推断模型语义成功，记录代理可观察的传输终态。管理入口独立于推理入口，管理员身份在服务端验证，查询和正文读取留审计记录。
- 按实际部署核对已开通的协议、日志开关、账号／Key 分配、请求 ID 透传、运行负载、保留期和正文采集用途后再开放真实流量。首期不引入 Kafka、独立身份服务、复杂权限策略或新的 BI 基础设施。

## Testing Decisions

- 以可观察行为、权限结果与最终统计值验证，不测试内部队列或解析函数的实现细节。项目没有应用代码和既有自动化测试，实施时须新增协议转发、日志同步、管理查询的端到端或集成用例。
- 转发与采集：原 Key 保留，SSE 拆包、慢客户端、取消与上游错误不改变推理结果；敏感字段、脱敏失败、超大媒体、关闭采集、队列满均不得泄露原文。
- 关联与统计：两个个人 Key、共享 Key、并发相同 Prompt、一个请求多条日志、日志延迟／重复／缺失、用量估算／缺失均有明确可观察结果；全量原生日志总量与有正文子集分开核验。
- 权限与生命周期：未授权或非管理员查询被拒；列表与详情均不能绕过校验；正文过期后不可查询，并检查异常日志与入口临时副本。
- 用实际部署版本和后端做小范围回放／灰度，核对源日志总量、身份映射、请求 ID 覆盖率和丢弃数；在可控故障下验证推理不受分析端故障阻断。

## Out of Scope

- 第一阶段不做离线分类、标签、场景比例／趋势、分类模型服务或人工标注；这些属于第二阶段。
- 不采集回答正文、媒体原件、system／assistant／tool 内容；不推断用户完成任务、采纳答案或生产力。
- 不做部门级权限、多租户与复杂身份策略；不通过共享 Key 猜测个人。
- 不建设 Kafka、ClickHouse、Langfuse、完整链路追踪或严格财务对账系统。

## Further Notes

现有研究基于 New API 源码提交 `e449cc700eb569cdfc2199cb73e97de46944f43c`；真实部署版本、日志后端、账号与 Key 分配方式均未现场核实。精简方案写有“每人独立账号或 Key”，但现有身份研究指出这尚缺部署证据，故将其列为上线前检查项。正文保存目的、告知方式及保留期需由实际使用方落实，本 PRD 不构成合规结论。

第二阶段启动条件：第一阶段请求 ID 关联、身份归属、原生日志总量和隐私边界验收完成；分类仅处理获准的脱敏文本，单独统计分类调用用量并显示分类覆盖率。
