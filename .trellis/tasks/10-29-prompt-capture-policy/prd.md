## 1. 目标与范围

让管理员能看到“用户提出了什么任务、请求携带了哪类上下文、消耗了多少 Token”，同时避免把源码、附件、工具结果和重复历史当作新的人工输入。

本期原则：**全量统计原生用量；按协议选择用户文本；代码与文件上下文默认不保存全文；无法可靠识别时明确降级。** “不采集”只影响分析副本，不能改变转发给 New API 的原始请求或 SSE 响应。

本期包含：现有四种推理接口的提取规则、脱敏与限长、采集字节计量与资源降级、管理员状态展示、对应测试与文档。人员归属继续使用可信原生日志的账号／凭证标识，不保存原始 Key。

本期不包含：修改 New API 源码、增加客户端 SDK、文件下载／OCR／内容索引、回答正文采集、会话重建、精确人工提问次数、LLM 分类服务、新消息队列或 BI 平台。`/v1/files`、multipart 文件上传等不新增正文采集；附件信息仅来自现有推理请求中可见的结构。

## 3. 采集策略

| 内容 | 本期处理 | 明确限制 |
| --- | --- | --- |
| 当前输入中的普通用户文本 | 提取后脱敏，按保存长度限制处理 | 标注为请求中选择的用户文本，不能保证就是本轮新写的人工指令 |
| 用户直接贴的小段代码并提问 | 允许保留有界的脱敏片段 | 不能遇到代码围栏就全部删除，否则问题失去上下文 |
| 协议明确标识的工具结果、文件正文、自动上下文 | 不保存正文；记录可见类型、数量等有限信息 | `role=user` 不足以证明是人写的内容；未知客户端包装不能靠猜 |
| 图片、PDF、文档、音频、Base64、文件引用 | 只记可见类型、数量、已有的大小信息 | 无大小则记未知；不下载文件，不解码媒体，不保存原始 URL、完整路径或文件内容 |
| 系统／开发者消息、助手回复、工具定义、历史上下文 | 不作为本期 Prompt 正文保存 | 不回退取旧问题来填补空白，不新增历史重处理任务 |
| 混在一个长字符串中的问题与材料 | 有可靠边界则按边界提取；无可靠边界则保存有限脱敏节选并明确标注 | 节选不等于已识别完整任务；超出解析预算时仅存元数据 |
| 调用与用量信息 | 保留请求标识、时间、接口、状态；全量同步原生 Token 与账号／凭证归属 | 无 Prompt 不能导致用量被排除；不能用已保存字符数反推 Token |
| 密钥、密码、Authorization、Cookie、私钥等 | 不进入分析队列、数据库或诊断日志 | 复用并补齐现有脱敏规则，不记录脱敏失败的原文 |

附件文件名不是本期必需字段。若确需展示，必须单独清理、限长；不要为了方便排查把签名 URL、文件 ID 或完整本地路径原样入库。工具／附件块数量仅表示请求中观察到的块，不能直接解释为新发生的工具执行或上传次数。

## 4. 提取、限长和降级规则

### 4.1 协议优先，禁止历史回填

- 明确支持 `/v1/chat/completions`、`/v1/messages`、`/v1/responses` 和 `/v1/completions`，分别按实际协议识别角色及内容块类型，不共用一个“有 text 字段就收集”的规则。
- Anthropic `tool_result` 可以放在 `user` 消息中；OpenAI 工具消息／Responses 工具输出也必须作为上下文处理。最新输入只有附件或工具结果时，正文为空并记录原因，不继续向前寻找旧问题。
- 如果最新输入同时包含工具结果与明确的普通用户文本，只保留允许的文本块；不把工具结果内嵌的 `text` 混入。
- 最新输入中出现未知类型时，保留未知标记；不能因为字段恰好叫 `text` 就把它认作用户指令。
- 客户端可能重发完整历史，纯文本也可能由客户端生成。没有可靠轮次标识就不提供“真实人工提问次数”，也不以相同文本去重后冒充该指标。
- 旧式 `/v1/completions` 缺乏角色结构，保留 `completion_prompt` 等明确范围标记，不承诺能区分人类指令与上下文。

协议核对参考：[Claude 工具返回](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)、[OpenAI 文件输入](https://developers.openai.com/api/docs/guides/file-inputs)。执行时以项目实际支持的格式和测试样例为准。

### 4.2 先选择内容，再脱敏，再生成保存文本

处理顺序为：**协议识别 → 选取允许的文本／元信息 → 脱敏 → 有界节选 → 异步保存**。原始请求按现有转发路径保持原样。

- 保留现有 `CAPTURE_MAX_CHARS`，本期不为每种文本再增加一套配置。
- 对有可靠边界的输入，优先保存任务文字，即使它位于大量材料之后。对未适配的客户端包装，明确标记未知，不依赖关键词声称已分离。
- 对解析预算内、没有可靠边界的长文本，默认采用头尾节选：总保存长度不超过 `CAPTURE_MAX_CHARS`，首尾各使用约一半额度，中间标出省略；省略标记也计入额度。记录“混合／长文本节选”范围和截断标记，不显示为完整指令。
- 必须先对候选文本脱敏，再截取头尾，避免切断密钥／私钥等结构后使规则失效。补充跨节选边界的敏感样本测试；脱敏失败只留元数据与安全错误码。
- 明确字符计数口径，不与 UTF-8 字节数混淆；节选不得产生残缺字符。
- 已由协议识别的文件正文和工具结果，不得通过“头尾节选”重新进入正文。

### 4.3 有界解析与真实字节计量

- 本期沿用当前有界 JSON 解析及大小预算机制，修正发现的边界问题；不因估算直接继续放大默认阈值。
- 增加实际观察到的请求体字节数与读取完整标记。计量来自收到的数据块，不能取 `Content-Length` 声明值，也不能复用停止采集后不再增长的 `capturedBytes`。
- 超过采集上限后仍继续计量实际经过代理的字节，前提是连接还在读取；取消或提前结束时标记不完整，数字只代表已观察到的部分。
- 请求体字节不含 HTTP 头／传输分块开销；如有内容编码，记录所观察编码下的大小，不虚称解压后大小。不为了统计额外解压大请求。
- 单请求上限、并发预算、解析错误、关闭采集、队列满等分别记录原因；采集放弃不能导致请求被截断、推理重试或 SSE 改变。
- 关闭正文采集时，不为分析复制或 JSON 解析请求正文；元数据计量和原生用量同步仍可工作。
- 核对预算预留与释放、缓冲引用释放及取消／错误路径。完整解析会产生 Buffer、字符串、JSON 对象等额外内存，不得把配置的缓冲预算宣传为 RSS 硬上限。

**后续可选项，非本期验收条件：** 如果实际观测表明大量有价值指令位于超过上限的请求中，再评估按 JSON 路径／内容类型做流式选择性解析。该方案仍需读取全流，不能用“取原始请求前后若干字节”代替。没有实测依据，不在本期引入流式解析库或自研解析器。

## 5. 最小数据与界面约定

优先复用 `capture_status`、`skip_reason`、`prompt_scope`、`prompt_truncated`、`extraction_version`、`redaction_version`。新增字节数、读取完整标记和必要内容概要时，使用明确类型及白名单；具体字段组织由执行 agent 按现有存储结构选择，不保存任意原始 JSON。

内容概要仅需覆盖已观察到的附件类型／数量、是否含工具结果或未知内容，以及确实已知的大小；不能为填满字段去获取文件。无解析结果时这些字段为未知，不能把“未知”显示为“没有”。

界面要求：

- 正文结果展示为“已采集文本／已截断／仅元数据”，同时保留关闭、过期、丢弃等现有运行状态。展示名称不要求再增加一套数据库枚举。
- “仅元数据”显示原因：主动省略附件／工具上下文、无可提取文本、不支持格式、超限、预算不足、脱敏失败等应能分辨。未知原因保留可解释兜底。
- 主动省略、资源超限和系统故障不能全部合并成“采集失败”。若展示比例，必须说明分母是哪些入口请求；未覆盖的文件上传接口不得算作已覆盖。
- 历史 `extract-v1` 记录按历史含义展示，不批量重写，不把旧“已采集”自动解释成已可靠识别的任务指令。
- 管理员鉴权与原生用量统计不回退。任何无正文请求，只要存在原生日志，都继续计入对应用户／凭证与模型的总用量。

| A13 | 同一测试集包含已采集、截断、仅元数据、超限和无关联请求 | 原生用量总量不被 Prompt 子集筛掉；缺失关联／用量保持原语义，不填成零 |
| A14 | 历史 extract-v1 数据、普通用户／未登录访问、分析队列满或写库故障 | 历史无误标、鉴权有效；故障不阻断推理，有可观察丢弃／失败记录 |
